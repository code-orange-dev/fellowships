# Developer Fellowship Reference

This page adds detail to the [Developer Fellowship](README.md). The track page and [Fellow Handbook](../FELLOW_HANDBOOK.md) are the day-to-day source of truth.

## The agreement in practice

| Topic | Working expectation |
| --- | --- |
| Term | Six months, with a documented Month-3 review |
| Time | Usually 15–20 hours/week part-time or 35+ for a full-time plan |
| Support | A primary mentor, fallback contact, peer feedback, and a clear check-in rhythm before the start |
| Reporting | A short weekly update and [monthly update](monthly-report-template.md) by the 5th |
| Work | A real contribution path in a Bitcoin FOSS project chosen with the fellow |
| Exit | A concise portfolio, handoff, and next 90-day contribution or funding plan |

## Contribution expectations

There is no universal PR quota. Projects vary in review speed, difficulty, and what “useful” means. Instead, a healthy fellowship has a clear contribution loop:

1. reproduce the build and learn local contribution norms;
2. identify a narrow problem with mentor or community input;
3. make the work visible through a branch, test, issue analysis, design note, review, or PR;
4. respond thoughtfully to feedback and record what changed;
5. increase responsibility only when the evidence supports it.

Tests, benchmarks, documentation, careful review, and design work count. Do not inflate work by splitting it into low-value PRs. Upstream maintainers control acceptance and timing.

## Suggested milestones

| Period | Question to answer | Example evidence |
| --- | --- | --- |
| Month 1 | Can I reproduce the environment and identify a useful first problem? | Build notes, test run, code-reading note, small contribution, refined plan |
| Months 2–3 | Have I established a sustainable feedback loop? | PRs or patches, review, test work, issue investigation, project discussion |
| Month 3 | Is the project, scope, and mentorship still right? | [Midpoint review](../templates/month-3-review.md) and 30-day plan |
| Months 4–5 | Am I deepening useful responsibility? | A substantial change, trusted review area, benchmark, or technical guide |
| Month 6 | Can someone understand and continue my work? | [Graduation portfolio](../templates/graduation-portfolio.md), handoff, next-step plan |

## Mentor relationship

The mentor helps with project orientation, scope, questions, and feedback. The fellow owns the work and communicates early when blocked. A mentor is not an outsourced code reviewer and does not control upstream acceptance. If the relationship is not working, contact the fallback person early rather than waiting for Month 3.

## Boundaries

This is not employment, a course, or a promise of funding after Month 6. It is structured runway for building a credible contribution record. A pause, scope change, or respectful conclusion is a valid outcome when it makes the work more sustainable.
